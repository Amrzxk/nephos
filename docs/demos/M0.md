# M0 demo: foundations and spikes

**What M0 delivers:** a repository others can contribute to, plus evidence that
the riskiest assumptions in [ADR-0003](../adr/0003-appliance-container-packaging.md),
[ADR-0004](../adr/0004-instances-as-system-containers.md) and
[ADR-0005](../adr/0005-nephos-owned-routed-network-plane.md) actually hold.

There is deliberately **no product to demonstrate yet**. `nephos` prints its
version and nothing else; M1 is the first milestone that does something. What
follows is replayable evidence, not a feature tour.

**Time:** about 25 minutes, most of it spent booting instances.

## Prerequisites

Linux with Docker Engine, or Windows with WSL2 and Docker Desktop. Go as pinned
in `go.mod`. See [DEVELOPMENT.md](../DEVELOPMENT.md).

Everything runs inside WSL, with the working copy on the ext4 filesystem.

## 1. The repository builds, lints, and cross-compiles

```bash
cd ~/src/nephos
make ci
```

Expect: `gofmt` clean, `go vet` clean, `golangci-lint` reporting **0 issues**,
unit tests passing with and without the race detector, and ten binaries built
across six platform targets.

```bash
go version -m dist/nephos_linux_amd64 | grep CGO_ENABLED
#   build   CGO_ENABLED=0
```

`CGO_ENABLED=0` on every shipped artifact is [ADR-0002](../adr/0002-go-for-control-plane-and-cli.md)'s
rule, and it is what makes the release matrix cross-compilable.

```bash
./bin/nephos --json
./bin/nephos-hook ; echo "exit=$?"     # exit=1 — the hook fails closed by design
```

## 2. The spikes

```bash
./spikes/run.sh all        # or sp1, sp2, sp3, sp4 individually
```

Each spike prints `PASS`/`FAIL` per assertion with the measurement beside it,
and writes machine-readable verdicts to `spikes/<name>/results/verdicts.tsv`.

A failing spike is a **result**, not an error. The reports in
[docs/spikes/](../spikes/) are what M0 actually delivers.

## 3. The recorded demo: a security group change blocking and allowing traffic

This is the part worth watching, and the one the
[ROADMAP](../ROADMAP.md#m0-foundations-and-spikes) asks for. SP3 does it
automatically; to watch it happen, run just that spike:

```bash
./spikes/run.sh sp3
```

Look for these three assertions in the `security group enforcement` section:

```
PASS  cross-subnet traffic allowed by a security group is reachable
      app -> web tcp/8080: reachable
PASS  same-subnet traffic is subject to security groups (ADR-0005 validation 2)
      peer -> web tcp/8080: timeout (want timeout)
PASS  blocked traffic times out rather than being refused
```

`peer` and `web` are in the **same subnet**. AWS still applies security groups
between them, because enforcement sits in front of each interface rather than at
a subnet boundary — and so does Nephos. A bridge-per-subnet design would have
switched that traffic in the kernel without consulting any rule.

Then the stateless network ACL trap, in the next section:

```
PASS  a NACL without an ephemeral-port egress rule breaks the return path
      app -> web tcp/8080: timeout (want timeout)
PASS  adding the ephemeral-port rule restores connectivity
      app -> web tcp/8080 after the fix: reachable
```

The connection **hangs** rather than failing, because the SYN-ACK is dropped on
the way back. Reproducing that faithfully is the entire point of enforcing on
real packets.

And the property that makes rule changes safe:

```
metric  atomic_replacements       100
metric  atomic_probe_attempts     84
metric  atomic_probe_allowed      0
PASS    100 ruleset replacements never briefly allow a denied flow
```

## 4. Nothing touched the host

```bash
ip -o link show | wc -l          # unchanged from before the demo
sudo nft list ruleset 2>/dev/null | grep -c 'table inet nephos'   # 0
ip netns list 2>/dev/null        # no nx-* namespaces on the host
```

Every namespace, veth, route and nftables table lives inside the appliance
container. SP3 asserts this from the inside too: the appliance's own root
namespace holds nothing but `lo` and its Docker uplink.

## What M0 changed about the plan

Four findings from the spikes feed directly into M1 and M2. Each produced a
plausible-but-wrong result first, which is why the spikes existed:

1. **cgroup v2 controllers must be delegated**, and the appliance must refuse to
   start if `memory`, `pids` or `cpu` cannot be — otherwise instance-type limits
   enforce nothing while the API reports them.
2. **`CAP_NET_ADMIN` must be added explicitly.** ADR-0004 has been amended;
   "default capabilities" contradicted its own R3.
3. **The AMI needs `APT::Sandbox::User "root"`**, or `apt` fails in every
   instance under `userns=auto`.
4. **Readiness must not be able to lie.** `ssh.socket` binds port 22 instantly,
   so a port check reported a healthy instance whose `sshd` had failed outright.
   The harness now requires a real `SSH-2.0-` banner.

Two more from SP4: the IMDS must serve **dated API versions**, not just
`/latest`, or cloud-init silently falls back to `DataSourceNone`; and
`ds-identify` disables cloud-init in containers unless its policy is forced.
