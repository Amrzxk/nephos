# ADR-0007: SQLite desired state with reconcilers

- **Status:** Accepted
- **Date:** 2026-09-17

## Context

The control plane must store resources, their relationships, lifecycle status, events, and lab progress for a single user on a single node. Several facts shape the design:

- Namespaces, veth pairs, routes, and nftables rules are kernel objects that **disappear when the appliance restarts**, so they must be rebuildable.
- Operations such as booting an instance are asynchronous and can fail halfway.
- `nephos reset` must be reliable.

## Options considered

**Store**

| Option | Pros | Cons |
|---|---|---|
| A. SQLite | Embedded; transactional; foreign keys enforce dependency rules (e.g., you can't delete a VPC that still has subnets); SQL for queries; one file on the volume; pure-Go driver keeps builds CGO-free | Single writer, which is fine at this scale; needs migrations |
| B. bbolt or Badger key-value store | Simple and embedded | Hand-rolled indexes and relations; no referential integrity |
| C. PostgreSQL | Robust | An extra process; overkill |
| D. etcd | Watch API | Operationally heavy; overkill |
| E. JSON/YAML files | Human-readable | No transactions; can corrupt |

**Control loop**

| Option | Pros | Cons |
|---|---|---|
| A. Imperative: handlers do kernel and runtime work synchronously | Simple at first | Partial failures leave inconsistent state; no rebuild after restart; long requests |
| B. Desired state + level-triggered reconcilers (Kubernetes controller pattern) | Idempotent convergence; restart means rebuild; heals drift; asynchronous operations come naturally; testable with fake engines | More upfront structure; brief visible "pending" states (realistic, since AWS behaves this way too) |

## Decision

Use **SQLite** as the single source of truth, with **level-triggered reconcilers**.

**Storage**
- SQLite in WAL mode with the `modernc.org/sqlite` driver.
- Queries generated by `sqlc`.
- Versioned migrations embedded in the binary and applied at startup.
- Foreign keys on.

**Request flow**
- An API handler validates the request, writes desired state and an `events` row in one transaction, enqueues reconcile keys, and returns the resource in a transitional state such as `pending`.

**Reconcilers and their keys**

| Reconciler | Key | Responsibility |
|---|---|---|
| `network` | per VPC, plus `edge` | Namespaces, links, routes, rules, rendered nftables ruleset |
| `compute` | per instance | Runtime create, start, stop, delete |
| `natgw` | per NAT gateway | NAT namespace and masquerade |
| `vpcsvc` | per VPC | DNS and instance-metadata listeners |
| `lab` | per lab attempt | Setup, fault injection, checks |

**Work queue**
- Only one reconcile runs per key at a time, with exponential backoff on errors.
- A full resync runs at startup and every 60 seconds by default.

**Status and events**
- Reconcilers write `state`, `state_reason`, and `observed_generation` back to the database.
- Events stream to clients over server-sent events.

**Kernel and runtime state is a cache**
- Startup rebuilds everything from the database.
- Objects that carry Nephos's `nx-` prefix or label but have no database row are garbage-collected.
- Objects without Nephos markers are never touched.

**Deletion and reset**
- Deletion follows AWS-style dependency checks (`DependencyViolation`).
- `nephos reset` marks resources for deletion in dependency order, waits for the reconcilers, then runs a leak checker: no `nx-vpc-*` or `nx-nat-*` namespaces, no Nephos containers, no leftover rulesets.
- `nephos reset --hard` skips the database entirely ([ADR-0003](0003-appliance-container-packaging.md)).

## Consequences

- Positive:
  - A restart, crash, or kernel-state loss is just "reconcile again".
  - The API stays fast.
  - Engines are easy to test in isolation.
- Negative / costs:
  - Generation tracking, ordered deletion, and idempotent engine operations must be designed carefully.
  - Users briefly see transitional states.
- Follow-ups:
  - M1 builds the reconcile framework with fake engines for unit tests.
  - `nephos state export/import` is post-MVP.

## Validation

- **M1:** state survives `nephos down && nephos up`, and `nephos reset` leaves zero leaks.
- **M8 chaos test:** 50 runs of killing `nephosd` with `SIGKILL` at random points during create and delete sequences. Every run converges to the database state with no leaks.
